# Deployment и admin guide

Этот документ собирает в один practical flow то, что администратору и внедренцу нужно знать для коробочного запуска WorkHub.

Цель инструкции:

- развернуть систему без догадок;
- выполнить первичную административную настройку;
- проверить, что инстанс действительно готов к эксплуатации;
- передать систему в рабочий запуск без зависимости от автора кода.

## Для кого этот документ

- для администратора инстанса;
- для внедренца;
- для технического специалиста, который делает первичный запуск или принимает систему после развёртывания.

## Что должно быть подготовлено до запуска

Перед началом убедитесь, что есть:

1. веб-сервер с поддержкой PHP;
2. MySQL/MariaDB;
3. доступ к файловой системе проекта;
4. доступ к CLI, чтобы запускать `php tools/...` команды;
5. домен или локальный адрес, по которому будет открываться система;
6. понимание, где будут храниться `uploads/`, `docs/`, `backups/` и `api/logs/`.

## Базовая структура, которую нельзя потерять

Для коробочной эксплуатации особенно важны:

- `api/config.php` — install-specific конфигурация;
- `manifest.json` — базовый public manifest;
- `uploads/` — пользовательские и прикладные файлы;
- `docs/` — шаблоны документов;
- `backups/` — backup-каталоги;
- `migrations/` — схема обновлений;
- `tools/` — CLI foundation для сопровождения.

## Шаг 1. Развернуть код приложения

Разверните проект в каталог веб-сервера вашим штатным способом.

После выкладки проверьте:

- каталог проекта открывается сервером корректно;
- PHP исполняется без фатальных ошибок;
- чувствительные каталоги не опубликованы как файловый листинг;
- папки `uploads/`, `backups/`, `api/logs/` доступны приложению на запись.

## Шаг 2. Выполнить первичную установку

Если инстанс новый, выполните штатную установку через `install.php`.

После установки убедитесь, что:

- создан `api/config.php`;
- приложение открывается по основному адресу;
- можно войти под административной учётной записью;
- базовые таблицы созданы корректно.

Если инстанс уже существующий, `install.php` повторно использовать не нужно.

## Шаг 3. Проверить health/readiness foundation

Сразу после развёртывания и установки выполните:

```bash
php tools/smoke.php --base-url=http://<host>
```

И отдельно проверьте:

```bash
curl -sS http://<host>/api/health
curl -sS http://<host>/api/ready
```

Что считать нормой:

- `/api/health` возвращает HTTP `200`;
- `/api/ready` возвращает HTTP `200`, если инстанс готов к работе;
- в readiness-checks нет критических ошибок по БД, каталогам и конфигурации.

Если `/api/ready` возвращает `503`, запуск останавливается до выяснения причины.

## Шаг 4. Привести инстанс к минимально безопасному профилю

После установки администратор должен проверить минимум:

1. приложение доступно по HTTPS;
2. `install.php` не остаётся в production-поставке без необходимости;
3. `api/debug.php` не используется на production;
4. `backups/` не раздаётся напрямую из веба;
5. `api/config.php` не доступен на чтение через веб-сервер;
6. права на `uploads/`, `backups/`, `api/logs/` минимально достаточные.

Подробный baseline описан в `instructions/17-security-baseline.md`.

## Шаг 5. Применить или проверить миграции

Для новой или существующей инсталляции используйте стандартный flow:

```bash
php tools/migrate.php preflight
php tools/migrate.php plan
php tools/migrate.php status
```

Если есть pending migrations и вы действительно выполняете обновление:

```bash
php tools/backup.php create --label=before-migrate
php tools/migrate.php migrate
php tools/migrate.php status
```

Полный update flow и rollback описаны в `instructions/15-update-and-release-runbook.md`.

## Шаг 6. Выполнить первичную административную настройку

После того как инстанс технически поднят, администратор должен пройти базовую настройку в интерфейсе.

Минимальный practical порядок:

1. проверить название приложения и компании;
2. загрузить логотип;
3. создать сотрудников;
4. назначить роли и проверить права;
5. проверить рабочие справочники и организационную структуру;
6. подготовить шаблоны документов;
7. при необходимости настроить интеграции;
8. выполнить короткую приёмку под администратором и обычным пользователем.

Подробный пользовательский стартовый порядок уже описан в `instructions/12-after-install-and-client-import.md`.

## Шаг 7. Проверить критичные бизнес-сценарии

До передачи системы в работу желательно вручную проверить хотя бы:

1. вход администратора;
2. создание сотрудника;
3. назначение роли;
4. открытие CRM и карточки клиента;
5. создание задачи;
6. открытие документов;
7. загрузку файла;
8. работу чата или заявок с сайта, если они используются.

Для release-level проверки дополнительно используйте:

```bash
php tools/smoke.php --base-url=http://<host>
```

## Шаг 8. Организовать эксплуатационный минимум

До продуктивного запуска нужно определить:

- кто отвечает за backup;
- где хранятся backup-каталоги;
- кто выполняет обновления;
- кто проверяет `/api/health` и `/api/ready`;
- кто просматривает audit trail при инцидентах;
- как фиксируются окна релизов и откатов.

Минимальные эксплуатационные опоры уже есть:

- backup/restore — `instructions/14-backup-and-restore.md`;
- update/runbook — `instructions/15-update-and-release-runbook.md`;
- audit trail — `instructions/16-audit-trail.md`;
- security baseline — `instructions/17-security-baseline.md`.

## Что передать заказчику или внутреннему администратору

После запуска у ответственной стороны должны быть:

1. адрес системы;
2. администраторская учётная запись;
3. список ролей и ответственных пользователей;
4. путь к backup-процедуре;
5. порядок обновления;
6. порядок проверки здоровья системы;
7. перечень подключённых интеграций и секретов;
8. понятный контакт, кто разбирает инциденты первого уровня.

## Частые ошибки при развёртывании

- система открывается, но `uploads/` или `api/logs/` недоступны на запись;
- администратор сразу начинает работать без проверки ролей и прав;
- не создан backup-процесс перед первым обновлением;
- `/api/ready` уже сигнализирует проблему, но её игнорируют;
- интеграции подключаются без фиксации endpoint'ов и shared secret'ов;
- на production оставляют installer/debug артефакты.

## Итог

Коробочный запуск WorkHub считается качественно выполненным не тогда, когда просто открывается главная страница, а когда:

- инстанс доступен и проходит health/readiness checks;
- базовая конфигурация и роли настроены;
- критичные сценарии проверены;
- backup/update/security foundation реально введён в эксплуатацию;
- администратор и внедренец понимают, как сопровождать систему дальше.
