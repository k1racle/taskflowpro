# Кастомизация без кода: что уже можно настраивать, а что нет

Этот документ фиксирует текущие границы no-code кастомизации в WorkHub.

Он нужен для трёх вещей:

- чтобы администратор понимал, что можно менять самостоятельно;
- чтобы внедренец не обещал лишнего;
- чтобы команда не лезла в БД там, где уже есть нормальный интерфейс.

## Главный принцип

Если настройка уже доступна через интерфейс или штатный API/CLI flow без правки исходников, это считается поддерживаемой кастомизацией без кода.

Если для изменения нужно:

- редактировать PHP/JS-файлы;
- менять SQL вручную;
- править config/env вне штатного сценария;
- дорабатывать бизнес-логику;

то это уже не no-code кастомизация, а техническое изменение инстанса.

## Что уже можно настраивать без разработчика

## 1. Роли и права доступа

Через административный интерфейс уже можно:

- создавать роли;
- изменять роли;
- удалять роли там, где это разрешено логикой системы;
- назначать права ролям;
- управлять доступом пользователей через роли и permissions layer.

Практический смысл:

- можно собирать доступы под отделы и функции компании;
- не нужно править БД вручную для обычного управления ролями.

## 2. Сотрудники и организационная структура

Без разработчика уже можно:

- создавать сотрудников;
- редактировать карточки пользователей;
- назначать роли;
- управлять отделами;
- связывать пользователей с оргструктурой в рамках существующего UX.

Это покрывает базовую коробочную адаптацию под конкретную компанию.

## 3. Отделы

Через штатный UI/API уже доступны:

- создание отдела;
- редактирование названия, описания и иконки;
- удаление отдела;
- просмотр связанных сотрудников, проектов и задач.

Это означает, что базовую оргструктуру можно поддерживать без доступа к БД.

## 4. Этапы задач

Через экран менеджера этапов уже можно:

- создавать этапы задач;
- менять название;
- менять цвет;
- менять порядок;
- удалять этапы.

Практический эффект:

- компания может адаптировать task-kanban под свою внутреннюю терминологию и процесс.

## 5. Подэтапы задач

Через тот же manager уже доступны:

- создание подэтапов;
- изменение названия и цвета;
- удаление подэтапов.

Это даёт единый справочник подэтапов без ручной правки данных.

## 6. CRM-воронки и этапы сделок

В текущем UI уже поддерживается управление CRM-структурой:

- создание и редактирование воронок;
- удаление воронок;
- создание этапов сделок внутри выбранной воронки;
- изменение названия, цвета и порядка этапов;
- маркировка `won/lost`-этапов;
- сохранение порядка этапов.

Практически это уже нормальная no-code настройка под разные схемы продаж.

## 7. Системные настройки приложения

Через административные настройки уже можно менять без разработчика:

- название приложения;
- данные компании;
- логотип и часть внешнего вида;
- отдельные интеграционные параметры;
- настройки Telegram в предусмотренных формах;
- часть email-related настроек;
- часть персональных пользовательских настроек.

Важно: конкретный состав полей зависит от текущего экрана настроек и уже встроенных модулей, но сам подход уже no-code.

## 8. Настройки виджетов сайта

Через встроенный UI уже можно:

- задавать API base;
- настраивать профиль виджета;
- менять позицию, размеры, тексты и brand-параметры;
- генерировать embed/script code;
- активировать нужный профиль.

Это полноценная no-code настройка внешнего встраивания без правки фронтенд-кода сайта CRM.

## 9. WooCommerce referral integration settings

Через CRM settings уже можно без разработчика:

- указать URL магазина WooCommerce;
- сохранить shared secret;
- скопировать webhook endpoint;
- скопировать visit endpoint;
- использовать встроенную подсказку по настройке плагина.

На стороне WordPress в самом плагине тоже доступны no-code поля:

- `CRM webhook URL`;
- `Shared secret`;
- `Cookie TTL days`;
- `Track visits`;
- тест соединения с CRM.

## Что пока НЕ считается кастомизацией без кода

Ниже границы, которые важно проговаривать честно.

## 1. Новые типы сущностей и новая бизнес-логика

Без разработчика пока нельзя:

- добавлять новые прикладные модули;
- создавать новые типы карточек/сущностей с полным циклом хранения и UI;
- добавлять новые workflow-движки;
- менять серверную бизнес-логику существующих модулей.

## 2. Произвольные пользовательские поля как универсальный конструктор

Сейчас в проекте нет подтверждённого общего конструктора custom fields уровня:

- «добавить поле в карточку клиента через UI»;
- «добавить новое поле в задачу без миграции»;
- «собрать полностью свои формы из конструктора».

Значит это пока не стоит продавать как готовую no-code возможность.

## 3. Полная настройка всех справочников в любом модуле

Часть справочников уже управляется через UI, но не все внутренние словари системы гарантированно вынесены в административные экраны.

Если для конкретного справочника нет штатной формы управления, он не считается закрытым no-code сценарием.

## 4. Свободное изменение структуры документов и шаблонизации на уровне движка

Документные шаблоны можно готовить и заменять, но:

- изменение логики генерации;
- добавление новых типов вычислений;
- изменение движка подстановок;

это уже техническая доработка, а не простая административная настройка.

## 5. Глубокая переработка UI, навигации и permission model

Без разработчика не стоит считать поддерживаемыми:

- изменение маршрутизации приложения;
- создание новых экранов;
- глубокую перестройку permission model;
- замену UX-паттернов или глобальной дизайн-системы.

## 6. Интеграции вне уже предусмотренных точек

Если интеграция не имеет:

- штатного settings block;
- документированного endpoint'а;
- встроенного UI или готового plugin/adapter слоя;

то её подключение уже требует разработки.

## Практическая граница для продаж и внедрения

Корректная формулировка на текущем этапе такая:

> WorkHub уже поддерживает важный слой коробочной no-code адаптации: роли, отделы, этапы, CRM-воронки, часть интеграций и системных настроек. Но это ещё не универсальный конструктор произвольных сущностей и полей.

Эта формулировка честная и сильная одновременно: она показывает реальную зрелость без завышенных обещаний.

## Как работать с запросом на кастомизацию

Если бизнес просит новую настройку, сначала надо определить, к какому типу относится запрос:

1. **Уже есть в UI** — обучаем администратора и не трогаем код.
2. **Есть в данных, но нет удобного экрана** — это хороший кандидат в следующий B3-шаг.
3. **Требует новой логики/структуры** — это уже разработка, а не административная настройка.

## Что логично развивать следующим шагом

Если продолжать B3 последовательно, самые сильные кандидаты такие:

1. общий каталог «что администратор может настроить сам» прямо в интерфейсе;
2. более явное управление справочниками и статусами из admin-раздела;
3. пользовательские поля для CRM/задач как отдельный следующий product step;
4. настройка шаблонов уведомлений без правки кода.

## Итог

На текущем этапе WorkHub уже имеет реальный слой кастомизации без кода, достаточный для типового внедрения:

- роли и права;
- сотрудники и отделы;
- этапы задач и подэтапы;
- CRM-воронки и этапы сделок;
- часть системных и интеграционных настроек;
- site widgets и WooCommerce referral integration.

Но границы нужно держать честно: универсальный no-code конструктор полей, сущностей и любой бизнес-логики пока не является готовой частью продукта.
